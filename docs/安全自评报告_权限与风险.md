# FutureLedger 安全自评报告：权限分级、控制措施与已知风险

**项目：** FutureLedger（未来账本）  
**文档用途：** 比赛提交材料  
**版本：** 2026-11-01

## 1. 自评范围与结论

本报告覆盖当前仓库中的 Text2SQL Demo、演示转账、现金流规划接口，以及已实现的 Execution Gate、Mock Bank 和 A/B/C 契约测试。系统使用合成用户、合成账户和合成流水，不连接真实银行。

总体判断：**适合本地比赛演示，不适合直接作为生产银行系统。** 当前已实现的主要保护包括用户会话隔离、只读 SQL 白名单、LLM 输出 schema 校验、密码复核、参数哈希、幂等键、额度重算、未知结果查证和结果脱敏。生产部署仍需要正式身份认证、MFA、PostgreSQL RLS、密钥托管、TLS、监控和跨进程恢复。

## 2. 保护对象与安全目标

保护对象包括：

- 用户身份、密码和登录会话；
- 账户余额、收入、支出、退款和转账流水；
- 收款人、转账金额和用途类别；
- LLM API key、模型配置和语义目录；
- 规划目标、现金流假设、操作计划和审计事件。

安全目标是：

1. 用户只能读取和操作自己的授权数据。
2. 查询可以自动化，写操作必须显式确认并经过强验证。
3. LLM 不能直接访问数据库写权限、修改余额或绕过业务规则。
4. SQL 注入、模型越权、重复扣款和未知银行结果不会被静默处理。
5. 用户看到的结果不泄露 SQL、内部 ID、其他用户数据或凭据。

## 3. 权限分级

|主体/角色|允许操作|明确禁止|
|---|---|---|
|未登录访客|访问登录/注册入口、查看静态页面|读取账单、创建会话、执行任何操作|
|已登录用户|读取本人授权账户的余额、流水和统计；创建查询/规划；发起转账预览|读取他人数据、直接提交 SQL、直接修改余额|
|已登录用户（高风险操作）|在参数不变且确认未过期时输入密码并确认转账|仅凭聊天文字执行转账；修改已确认金额、收款人或账户|
|LLM Provider|根据当前问题生成路由和结构化计划；解释结果|访问全库、决定权限、生成可执行写 SQL、读取密码/API key|
|应用 API|鉴权、schema 校验、权限判断、查询编译、状态机推进|绕过执行门直接写银行余额|
|SQL 只读角色|执行已编译的参数化 SELECT|INSERT、UPDATE、DELETE、DDL、跨主体查询|
|Execution Gate / Worker|核对确认、额度、幂等键，提交已授权操作并查证结果|改变用户意图、提高额度、把未知结果重试成第二笔付款|
|Bank Adapter / Mock Bank|提供账户事实和转账接口|接受未授权主体、重复扣款、破坏平衡分录|
|管理员/开发者|本地配置、测试和重置合成数据|把生产凭据提交到仓库或使用调试接口操作真实资金|

## 4. 数据访问控制

### 4.1 用户和会话隔离

会话绑定认证主体、数据集版本和账户范围。后端从 session/token 得到 `user_id`，不信任用户问题、IntentPlan 或请求体中的主体字段。导出接口也绑定 session，另一个用户的 session 不能下载原查询结果。

### 4.2 LLM 可见范围

模型只接收完成当前任务所需的最小上下文，例如当前用户的账户名称、可用类别/商户枚举和有限流水样例。不会发送其他用户、密码、API key、完整数据库、自由备注或完整历史流水。数据库执行结果和 SQL 不回传给模型作为自由推理材料；最终金额由后端计算。

### 4.3 数据分类

|分类|例子|处理原则|
|---|---|---|
|公开/演示|页面说明、合成类别|可用于比赛演示|
|用户账单数据|余额、收入、消费、退款|只在当前主体和授权账户范围内使用|
|高敏感认证|密码、session token、API key|不进入 LLM、SQL、Outbox 或普通日志|
|操作凭据|params_hash、authorization_id、idempotency key|绑定主体、参数版本和有效期|
|审计数据|request_id、状态、时间、银行引用|追加记录、脱敏展示|

## 5. 查询安全控制

查询采用“路由 → IntentPlan → 后端校验 → SQL 编译 → 只读执行”的链路。

- LLM 输出必须符合 Pydantic/JSON schema；无效字段、未知指标和未知枚举会被拒绝或要求澄清。
- 编译器只使用语义目录中的固定指标和维度，不接受模型直接传入 SQL。
- 只允许单条参数化 SELECT；拒绝 `DROP`、`DELETE`、`UPDATE`、`INSERT`、DDL、多语句和危险函数。
- 账户、类别、商户和日期使用绑定参数，不使用字符串拼接。
- 空结果不会删除用户过滤条件后返回总数。
- 查询结果隐藏内部 transaction ID、IntentPlan、SQL 和数据库凭据。
- 生产环境还应加 statement timeout、结果行数上限、只读事务和 RLS 双重约束。

## 6. 执行安全控制

转账流程采用状态机：

```text
DRAFT → NEEDS_CONFIRM → NEEDS_AUTH → READY
→ SUBMITTING → SUCCEEDED / FAILED / PENDING_UNKNOWN
```

控制措施：

1. 先展示金额、账户、收款人和用途，不能从一句聊天直接扣款。
2. 参数被规范化并计算 `params_hash`；金额或收款人变化会使旧确认失效。
3. 高风险或超过日累计阈值的操作需要密码复核/强验证。
4. 服务端重新计算日累计额度，模型和浏览器不能自行提高额度。
5. 使用稳定幂等键，重复请求只产生一次银行提交。
6. Outbox 与应用状态同事务写入，Worker 负责提交和恢复。
7. 银行响应丢失时进入 `PENDING_UNKNOWN`，先查询状态，不盲目重试。
8. 生产银行余额和分录只能由银行角色修改，Agent 数据库不能直接改余额。

本地 Demo 的转账只作用于合成账本，密码是演示认证，不代表生产级身份认证。

## 7. 规划功能安全控制

存钱目标和省钱建议走独立 planning 路由：

- LLM 只提取目标金额、期限、保留余额和约束；
- 后端先确认授权账户和数据范围，再读取必要的收入/支出数据；
- 金额、日期和最低余额由确定性现金流模拟器计算；
- 规划结果不会自动生成或提交转账；
- 用户必须另行发起执行类请求，执行门再次确认。

这样可以避免把模型的自然语言建议误当成银行操作，也避免把全量流水无条件发送给模型。

## 8. 已知风险清单

|风险|等级|当前状态|建议措施|
|---|---|---|---|
|Demo 登录不是生产身份认证|高|已知，明确限制为本地演示|接入 OAuth/OIDC、MFA、密码哈希、登录限速和设备会话管理|
|SQLite Demo 无生产级 RLS|高|已知，当前靠服务层主体过滤|生产改用 PostgreSQL 独立角色、RLS、`SET LOCAL` 和连接回收清理|
|LLM 可能误解意图或受到 prompt injection|中|有 schema、枚举、权限和 SQL 审计保护|增加模型评测、输入隔离、拒答策略和人工确认边界|
|LLM/API 服务商可能看到发送的上下文|中|只发送最小授权上下文|敏感字段脱敏、企业隔离 endpoint、供应商数据保留审查|
|模型输出错误日期或分组|中|日期规则、当前日期和后端 schema 校验|澄清机制、金丝雀测试、结果口径展示|
|错误分类影响支出统计|中|支持用途选择并保留分类来源|允许用户纠正、保留版本和审计变更|
|跨进程银行未知状态恢复不完整|高|同进程测试已覆盖，生产恢复仍待完成|持久化 bank reference、worker lease、重启查证和告警|
|API key 泄露|高|要求环境变量，不提交仓库|使用 Secret Manager、轮换、最小权限、日志脱敏|
|拒绝服务/昂贵查询|中|Demo 有限查询路径|速率限制、超时、行数/成本上限、队列隔离|
|前端路由守卫被绕过|中|后端仍应鉴权，前端只改善交互|所有 API 强制服务端鉴权，不信任前端状态|
|合成数据被误认为真实银行数据|中|README 和报告已声明|界面显示 Demo 标识，生产配置禁止默认合成凭据|
|转账标签错误导致统计口径偏差|低|转账确认时要求选择用途|提供修改标签但保留原始事实和变更审计|

## 9. 已执行的验证

仓库测试覆盖以下安全边界：

- 用户主体与账户范围隔离；
- 未知类别和越权账户拒绝；
- `DROP/DELETE/UPDATE/INSERT` 和多语句 SQL 拦截；
- 查询导出 session 隔离；
- 转账密码错误、参数过期、幂等重复提交；
- 日额度并发竞态；
- 银行成功但响应丢失后的 `PENDING_UNKNOWN` 查证；
- 规划模拟不修改账本。

推荐复核命令：

```bash
python3 -m unittest discover -s tests -q
python3 -m compileall -q demo services tests
git diff --check
```

测试通过只说明合成数据和本地模块符合当前测试契约，不等同于真实银行、生产身份系统或完整部署安全认证。

## 10. 自评结论

FutureLedger 已形成“LLM 负责理解、后端负责权限和口径、确定性代码负责计算、独立执行门负责写操作”的安全边界，足以支持比赛演示和功能验证。当前最高优先级的后续工作是生产级身份认证、PostgreSQL RLS、密钥托管、真实银行接入前的沙箱隔离，以及跨进程未知转账状态恢复。在这些工作完成前，系统应继续限制在合成数据和本地演示环境中。
